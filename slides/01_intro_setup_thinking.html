Course intro, setup, and the one skill that survives AI

The honest conversation

Every one of you will ask an AI to write code this semester.

That is fine. That is the job now.

The problem is that most first-time programmers cannot tell whether the code they got back does what they need.

This course exists to fix exactly that.

Demonstration

Syntax is free now

Prompt: “Write Python to test whether blood pressure differs between treatment groups.”

import pandas as pd
from scipy import stats

df = pd.read_csv("data/patients.csv")
group_a = df[df["group"] == "A"]["systolic"].dropna()
group_b = df[df["group"] == "B"]["systolic"].dropna()

t, p = stats.ttest_ind(group_a, group_b)
print(f"p = {p:.4f}")

p = 0.2152

It runs. It reports no significant difference. Do we write that up?

Demonstration

It ran. It was still wrong.

What actually happened

The group column contains "A", "B" — and "A ", with a trailing space, in 40 rows entered at a second site.

== "A" silently discarded those 40. Worse, they were the site with lower pressures — so the analysis ran on 201 of 250 patients and lost exactly the rows that mattered.

The same test, done right

df["group"] = df["group"].str.strip()

A: 129.4 mmHg  ·  B: 134.2 mmHg

p = 0.0064

There was a difference. The first version would have thrown it away.

The lesson

Nothing errored. Nothing warned. The AI cannot catch this, because it requires knowing something about your data that is not in the code.

We do not care whether you memorize syntax.

We care whether you can read a block of code and tell us what it does and whether it is right.

What this course is, and isn't

It is

  • The logic underneath the syntax
  • Reading code critically
  • Knowing what to ask for, in the right vocabulary
  • Knowing how to check an answer
  • Owning the analysis that carries your name

It isn't

  • Memorizing function signatures
  • A ban on AI (use it — we'll teach you how)
  • A software engineering course
  • A statistics course (though we'll cover enough to keep you out of trouble)

The corollary you cannot delegate

You are the scientist. The code has your name on it. If an AI wrote a bug and the paper is wrong, that is your bug and your paper.

By the end of today you can…

  1. Run a one-line program in Python and in R, in three different tools.
  2. Say in one sentence what a program is.
  3. Take a research question and break it into numbered steps a computer could do.
  4. Name one thing AI is reliably good at and one it is reliably bad at.
Objectives 2 and 3 are the ones we actually grade. Objective 1 is plumbing.

Segment 3 · the load-bearing 10 minutes

The hard part of programming is not the code.

The hard part is turning a research question into a sequence of unambiguous steps.

On the board — you tell me the steps

Research question

“Is average blood pressure different between patients on drug A versus drug B?”

What would a computer have to do, in order?

The decomposition

  1. Get the data — from a file, a database, wherever.
  2. Look at it. How many patients? What columns? Any missing values?
  3. Split patients into a drug-A group and a drug-B group.
  4. Compute the mean blood pressure of each group.
  5. Ask whether that difference is bigger than chance would give us.
  6. Report it — a number and a picture.

Now the reveal: that list is the syllabus

StepWhere we teach it
1. Get the dataSessions 6–7 — files, dataframes
2. Look at the dataSession 9 — exploratory analysis
3. Split into groupsSession 8 — filtering & wrangling
4. Compute group meansSession 7 — summarising
5. Test the differenceSession 11 — univariate statistics
6. Report itSessions 10 & 13 — visualization, communication

Sessions 2–5 are the grammar you need to write any of them.

Harder: your turn, in pairs

Decompose this

You have expression measurements for 20,000 genes across 100 tumor samples and 100 healthy samples. Which genes are most different?

Three minutes. Numbered steps. Be annoyingly specific.

Watch out for: what does “most different” mean? Different on average? Different relative to the noise? And you are about to run 20,000 tests — does that change anything?

When you ask an AI to “analyze my data,” it has to guess all six steps.

When you can name step 3 and step 5 in the right vocabulary, you get the right answer instead.

That is the entire value proposition of learning to code in 2026.

Segment 4 · 22–28 min

What AI is actually good at

Reliably good

  • Boilerplate — imports, plot styling, file reading
  • Syntax you forgot — “how do I open a CSV in pandas?”
  • Explaining unfamiliar code line by line
  • Suggesting libraries for a task
  • Refactoring code you already understand
  • Translating Python ↔ R

Reliably unreliable

  • Anything requiring knowledge of your data
  • Choosing the right statistical test
  • Noticing a column is text when it should be a number
  • Knowing whether a p-value means anything for your design
  • Small numerical slips — off-by-one, log vs log10, degrees vs radians
  • Hallucinating functions and packages that don't exist
Notice the pattern: the left column is form. The right column is meaning. AI is excellent at form.

So: always verify. Concretely.

1 — ExpectBefore you run it, say what the output should look like. Roughly how big? What shape? What sign?
2 — RunActually execute it. Do not reason about code you have not run.
3 — CompareDoes the output match what you expected? If not — which one of you is wrong?
4 — ExplainCan you say, line by line, why it produced that? If not, you don't own it yet.

The line worth writing down

If you have no expectation, you are not doing science. You are doing typing.
